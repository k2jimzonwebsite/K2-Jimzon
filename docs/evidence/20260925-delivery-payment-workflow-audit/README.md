# Delivery options, staff rates and payment workflow audit — 25 September 2026

**Owner question:** Can staff change delivery rates now, and does the delivery/payment workflow work end to end? This audit used source review, focused local tests, the exact live checkout, and read-only production SQL. It made no customer order, payment, rate, database, staff-account or deployment change. MAP-023 owns the remaining work.

## Short answer

The buyer sees delivery and GCash/MariBank choices. **Staff cannot currently publish a general delivery rate through the live Admin rate editor.** A separate live per-order delivery-details RPC exists, but changing one order is not changing the rate list and its current SQL permits a higher amount after checkout confirmation. The protected payment-evidence workflow is prepared locally, but the deployed direct Admin call and live payment function have incompatible arguments. Neither flow has a verified real staff/payment receipt.

## UI and workflow review

| Before | After required for acceptance | Why |
| --- | --- | --- |
| Checkout promises “no surprise charges,” while a live staff RPC can replace an accepted amount without a cap. | Preserve the customer's accepted fee; any exceptional change requires an explicit new quote, customer acceptance and recorded reason before payment. | The total shown to a buyer must match the amount staff collect. |
| Delivery Rates says “Try one order the way the storefront prices it,” but it uses exact-locality courier rows while checkout uses fixed region/weight values. | Label it clearly as a staff courier-cost pilot until one server-authoritative customer pricing source is chosen and connected. | A staff member could otherwise believe a published row changes the customer site. |
| Payment screen offers structured evidence and an independent-check checkbox, while the live direct RPC accepts neither its fourth argument nor a separate verifier. | Activate the reviewed protected payment command and production migration together; prove two different staff identities against a real receiving-account transaction. | The screen must save the facts it asks staff to enter and prevent self-verification. |

The current rulebook also contains two incompatible delivery models: the 16/20 September region/weight checkout matrix and the older §13 exact-locality pilot that forbids using region floors as customer quotes. The owner-approved pricing policy must be reconciled in the rulebook before a unified rate control is activated. Do not silently treat either source as the live Admin editor.

## Required workflow and repair order

1. **Choose one customer fee policy:** owner confirms whether the regional/weight matrix or exact-locality approved courier costs set customer charges, and who may approve rate versions. The current checkout matrix is the deployed behavior; this decision must reconcile the rulebook conflict.
2. **Make the server authoritative:** compute or validate the delivery option, destination, weight and fee on a trusted server boundary; reject a browser-supplied zero or altered fee except a valid pickup. Preserve accepted order amounts, and require a newly communicated, explicitly accepted quote for any exception. Cover replay, expiry and rate-version changes.
3. **Activate Admin rate management only after MAP-017/020 gates:** review and apply the delivery tables/command in migration order, deploy the signed Admin BFF, prove Admin allow/Staff deny, publish a test rate with evidence and reason, and show the exact customer quote changes only where policy says it should. Reconcile real carrier cost separately from customer charge. The rate editor must not be enabled against missing tables.
4. **Activate the payment boundary in order:** apply the structured evidence migration, enable the protected Admin command, verify the exact four-field save path and independent actor check. Owner/staff verify both QR recipients and counted stock; one real small transfer then proves evidence, separate receiving-account verification, packing, dispatch and buyer status. Keep COD off until separately accepted.
5. **Accept on exact live hosts:** buyer, Admin and Staff sessions, phone/desktop, one normal route plus pickup and an exceptional/manual quote; test rejected/uncertain payment, changed rate, lost response and recovery. Record the order reference, rate version, signed command receipts, payer evidence, actual carrier receipt and rollback in MAP-023/025.

**Recovery:** No state changed in this audit. The current safe handling for any price mismatch is to pause fulfillment, inspect the exact order amount and customer communication, and seek explicit customer acceptance before changing a charge. Do not mark payment verified or hand a parcel to a courier while the payment path is unverified. Later migration/deployment rollback must follow the named MAP-017/020 release runbooks and preserve order/payment history.
