## Staff workflow after installation and release

1. Verify the exact existing SKUs represent variants of one product and share their current canonical brand/category state. Similar names alone are insufficient. Keep each SKU's publication, Website, price, stock, photos, label and Knowledge decisions separate.
2. In Inventory, select the related rows and choose **Manage variations**. The editor reads the complete existing family before editing. A selection spanning multiple families refuses; explicitly review/remove existing membership first rather than implicitly moving products.
3. Enter the mother product name. Add only needed types, such as Flavour or Weight, and exact values for every SKU. Values need one consistent spelling and unique complete combinations. Do not invent weight, flavour, colour or another dimension from unknown package information. Remove an unnecessary type or member explicitly.
4. Save once. The canonical command checks Admin/SuperAdmin, AAL2, original actor, signature, literal request, version, taxonomy and membership in one transaction. It records grouping events and a receipt, without changing inventory or orders. Reopen and verify the complete family before accepting the result.
5. In the storefront, confirm one discovery card, the intended choices and exact SKU URL/price/facts/availability for each option. Only dimensions with differing publicly eligible values get selectors; a one-value dimension appears as a read-only SKU fact. A single eligible member has no selector. An unlisted/unpublished sibling contributes no public label, count or price. Public reads suppress a family if later taxonomy assignments become inconsistent.

Small choice sets use wrapping 44px controls; larger sets use a labelled native select. A sparse combination names other values that will change before selection. Customers can inspect a sold-out SKU, but only its own stock determines whether it can be added. Different SKUs remain separate cart/order lines; historical orders keep their original SKU/name snapshots.

## Saved and uncertain decisions

An uncertain save preserves its original actor, literal body and key in this browser. Do not clear storage, hand it to another actor, create a replacement key or repeatedly click Save. Reopen **Review pending product variations**, sign in as the original eligible actor and explicitly retry the saved request. The matching cross-tab Web Lock prevents simultaneous dispatch. A receipt acknowledges the original decision, not a fresh current-state read.

A confirmed version refusal enables **Review latest grouping**. That path rechecks the original decision and reads/validates the latest family membership together with the original pending candidate SKUs before allowing a new edit. If another actor ungrouped first, a family-identified empty snapshot is valid only when the request names that family and has no selected SKUs or members; candidate product records are still read and validated. Review all current members and candidates; no old unsaved patch is silently reapplied. Loading/missing dependency/role/membership/taxonomy failures must be resolved before another decision. A network error preserves the original request.

To remove grouping, read the latest family and choose **Ungroup all members**. This releases only membership and preserves event/receipt history. To change one member's independent Product Master facts or Website assignment, use their existing protected workflows; the variation editor does not grant that authority.
