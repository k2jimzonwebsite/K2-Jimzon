  cover Postgres/pooler connections and exclude documented HTTPS application

- [Hosted roles](https://supabase.com/docs/guides/database/postgres/roles-superuser)
  do not give the customer postgres role unrestricted superuser access. This

## Options to decide

### 1. Owner-coordinated installation window — recommended operational candidate

One named database release coordinator performs the approved installation.
Other people and automation with privileged database access defer schema,
permission, role/membership, event-trigger and managed-setting changes for the
installation interval. Ordinary staff/customer business commands and rate edits
stay in scope for available service; actual contention and real-host availability
still require evidence and are not certified by this rule.

This uses coordination rather than a new application pause feature, broader
catalog grants, credential rotation or unqualified network/JIT settings.
Implementation would first need an owner-confirmed boundary and reviewed
inventory of privileged access/automation, explicit beginning/end of the interval,
and exact same-target capture/reconciliation/rollback evidence.

Tradeoff: this narrows the original simultaneous-privileged-change requirement.
It cannot physically stop a noncooperating privileged session or independently
prove no transient change occurred. Matching before/after captures do not repair
that limitation. Provider-managed activity is outside demonstrated tenant
coordination. Release remains inadmissible until that residual boundary is
explicitly accepted and the selected controls are actually qualified.

### 2. Provider-supported enforced exclusion

Keep the original stronger requirement and obtain a documented, reachable
provider mechanism that excludes every in-scope privileged mutation for the
entire transaction. Qualify its actual coverage, established sessions, platform
automation, acquisition/release/failure recovery and business availability without
changing captured permissions or deadlines.

Tradeoff: it provides the desired enforced boundary only if a suitable mechanism
exists and passes actual evidence. None has been established. JIT, network
restrictions, CLI deployment serialization and ordinary advisory locks are not
substitutes for that guarantee. No support message or provider change is
authorized by this brief.

### 3. Retain the strict gate without production activation

Preserve the current requirement and passing local work until an enforced
approach is established. This requires no new operational assumption but leaves
the production activation dependency unresolved. It is not full production
completion and does not justify repeating accepted tests or creating side work.
