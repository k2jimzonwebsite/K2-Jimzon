## Decisions and alternatives

1. Use a single authoritative conditional journal head for all register/cancel/authorize/generation transitions. Reject separate cancellation and authorization records that can both win.
2. Store immutable candidate events before committing the head, then immutable commit markers and a separate Durable Object SQLite witness before acknowledging a decision. Reject an outbox exported only after deletion and a journal in the same database backup.
3. Use the Durable Object as a serialized derived index and independent latest-head witness, not as a second business database. Reject eventual-consistency KV for decisions. SQL transactions cannot span R2 I/O; every gap has explicit reconciliation below.
4. Cloudflare R2 plus a SQLite-backed Durable Object is a concrete candidate because the owner's account is reachable. R2 is not enabled and no binding/storage guarantee has been tested in K2. Alternatives considered were a same-database journal (insufficient after restore) and a second database with a remote outbox (same cross-store ordering issue plus another operational service). Selection for production is not implied.

R2 documents atomic conditional writes and strongly consistent direct operations ([consistency](https://developers.cloudflare.com/r2/reference/consistency/)); its Workers binding supports conditional ETag matching ([API](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/)). A failed condition returns null; an exception/timeout is an unknown outcome, not a failed write. [Durability](https://developers.cloudflare.com/r2/reference/durability/) describes persisted acknowledgments and explicitly distinguishes durability from availability and deletion protection. Durable Object [SQLite storage](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/) and [state/concurrency](https://developers.cloudflare.com/durable-objects/api/state/) provide the other primitive, not an atomic transaction across providers.

## Authoritative records

All bytes use a versioned canonical JSON encoding. Fixed project identity is `pixplcjqivlfflickobf`; deployment pins an independently retained random genesis/namespace identity. Bootstrap is an explicit operator action; an absent head is never recreated by normal requests.

| Record | Contract |
| --- | --- |
| Current head | Small R2 object: format/project/genesis, monotonic revision, unique revision nonce, generation, mode (`active`/`recovering`), last event key/hash and predecessor hash. Every mutation uses the exact observed ETag. Never write an unconditional head or repeat identical head bytes (ABA). |
| Logical command | Create-once `commands/<operation ID>` stores the exact canonical command/payload hash independently of any predecessor or revision. Reusing that ID with different logical bytes refuses even after an unsuccessful candidate attempt. |
| Candidate event | Separate create-once attempt key derived from logical command hash plus predecessor head hash; records the operation ID, canonical command hash, predecessor, resulting revision/generation and deterministic unique revision nonce/event hash. The same attempt has identical bytes; a rebase has a different attempt key. Immutable private object. An orphan candidate is not authorization. |
| Commit marker | Create-once `commits/<padded revision>` containing the committed event/head hash, predecessor and generation. Only a verified head winner may be sealed. Conflicting marker bytes stop processing. |
| Durable Object witness/index | SQLite transaction stores applied revision/hash/genesis/generation and derived request states, actor's open request and exact operation results. It may advance only by replaying verified sealed events. It cannot invent or reverse a decision. |
| Erasure manifest | Immutable versioned object with original Auth/customer UUIDs (customer can be absent), exact scoped row IDs/associations, allowed field classes and protected-retention branch. No erased content. Hash/key are in the authorization event; a digest without retrievable bytes is insufficient. |

The authority accepts only registered schema-versioned command fields and bounded canonical payloads. It retains exact operation ID/payload hash/results. Changed bytes under an existing operation ID refuse. Timestamps do not establish ordering. Unknown formats, counters, project/genesis, signatures, association maps or manifests refuse; no permissive default verifier.

Every command needs an authenticated, purpose-bound adapter result matching its exact actor/request/generation and command hash. The local default denies all commands, not only authorization. Registration requires the current verified signed-in customer identity; cancellation requires the original actor; fence/activate require the separately held operator authority. Expiry requires a qualified worker and a committed native expiry decision that prevents subsequent verification and proves the request is still unverified. A verified held request cannot expire merely because its original code deadline passed. These adapters remain unqualified; passing a caller-selected role, boolean or timestamp is not authentication.

## State machine and commit boundary

`register` creates one undecided request for an original Auth UUID; it does not prove fresh closure verification. A second open request for the actor refuses. A known terminal operation returns its exact prior **receipt**, independently of current execution permission. A new request after cancellation/expiry must have a new ID and current verified database authorization. An authorized original Auth UUID cannot be registered again. A later account with the same contact has a different UUID.

For an undecided request, `cancel`, `expire` and `authorize` compete through the same head CAS. The first committed event is the sole winner. Cancellation/expiry are terminal non-deletion outcomes. Authorization is terminal processing authority, not physical deletion completion. A request's customer association is fixed by its authenticated committed freeze/manifest at authorization, rather than inferred from a reused contact or stale registration snapshot.

Each command is processed under the single coordinator's input exclusion, with a bounded deadline; correctness still depends on R2 CAS, not a JavaScript queue surviving a crash:

1. Read the direct current head and compare the persistent witness. Reconcile any newer committed chain before deciding. Verify the preceding head's marker; an unsealed head blocks competing decisions until that exact winner is sealed.
2. Create/verify the immutable logical command independently of a candidate attempt, then validate it against reconstructed current state and its exact operation identity. `authorize` additionally requires a verified committed freeze proof and retrievable matching manifest for the currently active database generation. Derive/write its immutable candidate attempt for this predecessor with create-once semantics and verify exact bytes.
3. CAS the current head from the observed ETag to the candidate's unique next head. Null means a competing commit: reread/reconcile. A timeout remains unknown. Never report failure/cancellation from a negative read. Reconcile the same operation; a conditional contender cannot overwrite a later head.
4. After establishing that the candidate is on the committed head chain, create/verify that revision's exact commit marker. No subsequent revision may be proposed while the current winner is unsealed. Lost marker acknowledgments retry the same create-once key/bytes; an incompatible object refuses.
5. Transactionally replay the sealed event into the SQLite witness/index, storing the exact operation result and monotonic head in one local transaction. Only after this acknowledgment may the service report cancellation/authorization or issue deletion permission. Reconcile an unknown SQLite acknowledgment from its durable state; do not repeat an external side effect.

If an attempt loses CAS to an unrelated event, reconcile first: if the logical operation is already committed, return its exact receipt; otherwise revalidate the same immutable logical command against the newer state and derive a new predecessor-bound attempt. Do not overwrite its old candidate or change the command bytes. Two attempts for one operation cannot both commit: same-parent contenders share an attempt; an older-parent ETag cannot commit after the head advances; after reconciliation the stored logical result prevents rebasing an already committed operation.

The response contract separates `receipt` (immutable operation ID/hash, outcome, committed revision/generation and scope references) from `execution` (a current capability projection). Historical receipts remain readable while recovering and after generation changes; they never issue deletion authority. The local core always returns `execution.allowed=false`. A future, separately qualified permit adapter must check active current head/generation, the exact original decision/manifest and current committed database freeze/instance, then bind a short-lived, non-replayable permit to that database generation and scope. It must default-deny and cannot run while recovering. Offline replay uses a distinct operator recovery contract. No historical retry or `authorized` string substitutes for this permit. This module boundary keeps present unqualified direct/worker paths inactive; it does not remove the full-goal integration requirement.

A head advanced without a marker/witness still identifies the logical winner; until sealed/witnessed it is reported as checking/processing uncertainty. There is no second cancellation boundary at a database flag or a response timeout. A losing cancel reports processing started only after the authorization is verified. An authorization loser never performs database/provider work.

## Crash, rollback and generation handling

Every cold start or explicit restore reconciles direct head, immutable commit-marker history and SQLite witness before serving decisions. Marker listing must traverse all pages and validate continuity through the pinned genesis. It may be bounded per pass, but an incomplete scan means not ready, never an empty history. A higher witness/marker revision than the head, a fork, a missing committed event or an unknown namespace is an integrity failure; normal requests may not repair it by overwriting evidence. An index behind a verified newer chain is rebuilt from that chain. A crash after head CAS is finished from the exact candidate; a crash after marker/witness returns its saved result.

Pagination is not a multi-object snapshot: capture the head before scanning and reread its exact ETag/hash after the final page. If it changed, reconcile/repeat against the new head within the budget; do not declare a concurrent legitimate advance to be corruption. Only an unchanged fresh head can establish a contradictory higher marker/witness. A later in-flight CAS can still race the next command, whose own ETag condition resolves that race. A permanently changing head or exhausted scan budget returns not-ready uncertainty, never an incomplete ready state.

`fence` is an operator-only event on the same CAS head, increasing the generation and setting mode `recovering`. Old-generation events read before the fence either committed earlier and are included, or their stale ETag refuses. After rereading, a request carrying an old generation/proof still refuses. No old writer may substitute the new generation or obtain its proof key. While recovering, reject normal registration, cancellation, authorization and outcome writes. Recovery reads/reconciliation remain available to the separately authenticated operator. `activate` requires the exact fenced head/generation and a verified reconciliation receipt; only then can new-generation decisions resume.

This fences journal decisions; it does not by itself fence Supabase, PostgREST, Auth, Storage or an old scheduler. Before a database rollback/promotion, actual provider/client entry points must be held closed and in-flight conflicting database work drained. A new database generation and proof key are installed only in that isolated database. Every acknowledged freeze must survive ordinary lossless failover; any failover that can lose it requires the same closed recovery procedure. These are unqualified deployment contracts, not capabilities inferred from an environment variable.

An older backup cannot be opened merely because its own journal copy is consistent. Recovery reads the live authority/witness/immutable history, verifies the fenced latest head, fetches all authorized manifests and applies each version's exact suppression. It distinguishes cancelled/expired requests from authorizations, preserves protected financial/shared records and later Auth UUIDs, and refuses unknown schema/field/relationship mappings. Access denial by original Auth UUID must work even if that UUID/row did not yet exist in the old backup; the current FK-bound tombstone alone cannot satisfy that case. Auth and object Storage reconciliation are separate explicit results. Service remains offline until replay, exact retry and provider/access checks pass.

## Database and user integration contracts

The existing direct command, scheduled eligibility worker and provider cleanup must all consume the same verified authorization; their present bypasses must be removed before activation. A short database transaction rechecks proof/contact, current identity/role, all real holds and policy, locks actor/customer/request in the established order and commits a frozen manifest/proof. It does not hold a PostgREST transaction open over remote I/O.

During that freeze, all conflicting writers must lock/check the same customer/actor barrier: accounts/claims/contacts/grants/scopes/channel identities; customer fields/settings/notifications; order/Pasabuy/wholesale lifecycle and dependent records; conversations/messages/events; explicit holds; and relevant Auth contact changes. Coverage must be derived from the actual schema's relationship graph and actual mutation entry points, with in-flight and direct-role tests. The current selected-column `enforce_open_customer` trigger is insufficient. No background callback may bypass the barrier. A verified cancellation permits unfreezing; an authorization holds the frozen decision through minimization/reconciliation. A missing/untrusted authority result leaves it frozen and visible for recovery.

Customers and staff need separate states for actual operational holds, waiting for a secure recovery record, frozen/checking an uncertain decision, authorized processing, local closure, pending provider cleanup and remaining retained/external/backups work. Saved operation identity survives response loss/reload. An authority delay must not be labelled an open order or promise continued access. Cancellation remains requestable before authorization, but success is reported only from its witnessed result. No repeat OTP is required solely because a processing response was lost. Immediate eligible processing and automatic resumption remain the target, subject to actual verified delays.
